## 0. Кратко (TL;DR)

- **СУБД:** SQLite, один файл `server/data/app.sqlite` (в Git не попадает).
- **Драйвер:** встроенный модуль Node.js `node:sqlite` (нативных зависимостей нет).
- **Версия Node.js:** минимум `>=22.13.0`, рекомендуется **Node 24 LTS** (см. раздел 4).
- **Схема:** 9 рабочих таблиц + служебные `user_roles`, `sessions` и `schema_migrations`.
- **Миграции:** `server/src/db/migrations/*.sql`, прогоняются `npm run migrate`.
- **Тестовые данные:** `npm run seed` (идемпотентно), полный сброс — `npm run db:reset`.

Команды (из папки `server/`):

```bash
npm run migrate     # применить неприменённые миграции
npm run seed        # залить/обновить тестовые данные
npm run db:recreate # удалить файл базы, создать заново и применить все миграции (без данных)
npm run db:reset    # удалить файл базы и пересоздать с нуля (миграции + тестовые данные)
```

`db:recreate` и `db:reset` удаляют файл базы — при `NODE_ENV=production` они
заблокированы (см. `server/src/db/guards.js`).

## 1. Как устроена база и как структура связана с логикой проекта

### 1.1. Таблицы

| Таблица | Назначение |
|---|---|
| `studios` | Настройки студии (одна строка): название, адрес, часовой пояс, валюта, общие часы работы |
| `users` | Аккаунты для входа; хранится только **хеш** пароля (роли — отдельно, в `user_roles`) |
| `user_roles` | Роли пользователей **списком**: у одного аккаунта их может быть несколько (`admin`, `master`, `client`) |
| `sessions` | Серверные сессии: хранится **хеш** токена и срок жизни; сам токен — только в cookie |
| `masters` | Профили мастеров, видимые на форме записи |
| `clients` | Клиенты (имя, телефон) для повторных визитов; **пароля тут нет** |
| `services` | Услуги: название, описание, длительность, цена |
| `master_services` | Связь многие-ко-многим «мастер ↔ услуга» |
| `master_schedules` | Повторяющийся недельный график мастера |
| `time_blocks` | Разовые блокировки времени (выходной, обед, личное) |
| `bookings` | Записи клиентов: кто, к кому, на что, когда, статус |
| `slot_holds` | Временные удержания слотов при оформлении записи; привязаны к пользователю и сроку жизни |
| `schema_migrations` | Служебная: учёт применённых миграций (создаёт прогонщик) |

### 1.2. Связь с клиентскими экранами

Карта «экран → данные» (подробно — в `docs/ui-map.md` и `docs/db-schema.md`):

- **Лендинг** (название, адрес, часы; услуги и мастера) → `studios`, `services`,
  `masters`, `master_services`.
- **Авторизация** (вход, регистрация, сессия) → `users`, `user_roles`,
  `sessions`, `clients`.
- **Запись и подтверждение** (услуги, мастер, дата/время, данные клиента,
  удержание слота) → `services`, `masters`, `master_services`, `clients`,
  `slot_holds`; **свободное время вычисляется** из `master_schedules` +
  `bookings` + `time_blocks`.
- **Успех, кабинет, детали, перенос и отмена** → `bookings` и связанные
  `services`, `masters`, `clients`.
- **Админ-панель** — следующая итерация; API `/api/admin/*` уже использует эти
  таблицы.

### 1.3. Соглашения по данным (единые для всей базы)

- **Абсолютные моменты времени** — `TEXT` в формате **ISO-8601 UTC**:
  `YYYY-MM-DDTHH:MM:SSZ` (например `2026-10-22T14:00:00Z`).
- **Даты без времени** — `YYYY-MM-DD`.
- **Длительности** — целые минуты, `INTEGER`.
- **Время в недельном графике** — `HH:MM`, «настенное» местное время студии.
- **Деньги** — целые числа в **копейках**, `INTEGER` (1500 ₽ = `150000`).
- **Флаги** — `INTEGER` 0/1 (`is_active`).
- **Внешние ключи** включены (`PRAGMA foreign_keys = ON`).
- Часовой пояс студии хранится в `studios.timezone` (`Europe/Moscow`, UTC+3) и
  применяется при показе и сопоставлении с графиком, но не в «моментах».

### 1.4. Логика свободного времени (важно!)

**Отдельной таблицы слотов нет и быть не должно.** Свободное время —
производная величина и вычисляется в момент запроса:

```
свободные интервалы = график (master_schedules)
                    − блокировки (time_blocks)
                    − активные записи (bookings: pending/confirmed)
```

Затем промежутки нарезаются на слоты, кратные длительности услуги. Полный
алгоритм — в `docs/db-schema.md`, раздел 6.

### 1.5. Где что лежит в коде

| Что | Файл |
|---|---|
| Схема (DDL) | `server/src/db/migrations/*.sql` |
| Прогонщик миграций | `server/src/db/migrate.js` |
| Тестовые данные | `server/src/db/seed.js` |
| Полный сброс базы | `server/src/db/reset.js` |
| Подключение к SQLite | `server/src/db/connection.js` |
| Единственная вставка записи (`insertBookingRow`) | `server/src/db/bookings.js` |
| Защита dev-команд на проде | `server/src/db/guards.js` |
| Конфигурация (путь к БД, env) | `server/src/config.js` |
| Хеширование паролей | `server/src/auth/password.js` |
| Создание/перенос/отмена записей | `server/src/api/booking-service.js` |
| Сессии и права (роли, проверки) | `server/src/api/session.js` |
| Ограничение частоты запросов | `server/src/api/rate-limit.js` |

## 2. С какими сложностями столкнулись и как их решили

### 2.1. В SQLite нет типа «дата/время»
**Решение:** хранить моменты как `TEXT` в ISO-8601 UTC. Такой формат корректно
сортируется как текст, читается глазами и работает с функциями `date()`,
`strftime()`. Альтернативы (Unix-число, Julian) отвергли: нечитаемы/дробные.

### 2.2. Деньги и ошибки округления
**Решение:** все суммы — целые в копейках (`INTEGER`). Никаких `REAL`.
Валюта — отдельное поле `currency` (ISO-4217, `RUB`).

### 2.3. Быстро устаревающие «слоты»
**Решение:** не хранить слоты в БД, а вычислять свободное время «на лету»
(раздел 1.4). Иначе пришлось бы синхронизировать кэш слотов при каждой записи,
блокировке и правке графика.

### 2.4. Пересечения брони
SQLite не умеет ограничения «диапазоны не пересекаются». **Решение:**
частичный уникальный индекс `uq_bookings_master_start_active` ловит совпадение
`(master_id, starts_at)` у активных записей (`pending`/`confirmed`). Полную
проверку перекрывающихся интервалов должен делать уровень приложения (в
транзакции) — это осознанный компромисс.

### 2.5. Роль `client` и клиенты без пароля
Изначально `users.role` допускал только `admin`/`master`, а у клиентов пароля
не было вовсе (регистрации нет). Понадобилась учётная запись клиента.
**Сложность:** SQLite **не умеет** менять `CHECK`-ограничение через `ALTER`.
**Решение:** миграция `003_users_role_client.sql` пересобирает таблицу по
официальной процедуре: `CREATE users_new` → копирование строк →
`DROP TABLE users` → `RENAME`. Так как на `users.id` ссылается `masters.user_id`
с `ON DELETE SET NULL`, на время миграции внешние ключи **отключаются** — иначе
`DROP TABLE users` обнулил бы связи. После прогона ключи включаются и
выполняется `PRAGMA foreign_key_check` (см. 2.7). Контактные данные клиента
по-прежнему хранятся в `clients` (там пароля нет); учётная запись для входа —
отдельно в `users` с ролью `client`.

### 2.6. Нативный драйвер `better-sqlite3`
Первоначально использовался `better-sqlite3` — он требует нативной сборки
(или готового бинарника под конкретную версию Node). На BeGet это риск:
сборка может потребовать компиляторов. **Решение:** перешли на встроенный
`node:sqlite` (раздел 3). Зависимостей в `server/package.json` больше нет.

### 2.7. Целостность при миграциях
Так как миграции могут пересобирать таблицы (см. 2.5), в `migrate.js`:
- внешние ключи отключаются на время прогона (`PRAGMA foreign_keys = OFF`
  нельзя менять внутри транзакции, поэтому — до начала и обратно после);
- каждая миграция применяется в собственной транзакции (`BEGIN`/`COMMIT`/
  `ROLLBACK`), учёт — в `schema_migrations`;
- в конце выполняется `PRAGMA foreign_key_check`; при нарушениях прогон падает
  с ошибкой.

### 2.8. Различия API `node:sqlite` относительно `better-sqlite3`
- Нет помощника `db.transaction()` → транзакции вручную (`BEGIN`/`COMMIT`/
  `ROLLBACK`) в `migrate.js` и `seed.js`.
- Нет `db.pragma()` → `PRAGMA` выполняется через `db.exec(...)`.
- Имя класса зависит от версии: в старых Node это `DatabaseSync`, в новых —
  `Database`. В `connection.js` используется шим:
  `sqlite.Database || sqlite.DatabaseSync`.

### 2.9. История миграций и дубли
Первая init-миграция `001_init.sql` была заменена на `002_init.sql`, чтобы не
держать схему в двух файлах. Позже возник дубль миграции, добавляющей роль
`client` (два файла с номером `003`) — оставлен один:
`003_users_role_client.sql`. **Правило:** не переиспользовать номера и не
редактировать уже применённые миграции; изменения — новой миграцией.

### 2.10. Безопасность на проде
- `server/src/db/guards.js` запрещает `db:reset` и `seed` при
  `NODE_ENV=production` без явного `ALLOW_DESTRUCTIVE=1`.
- `server/src/config.js` больше не хранит секретов: сессии серверные, ключ
  подписи не нужен (в БД лежит только хеш случайного токена). Единственный
  секрет — сам файл `.env` (в Git не попадает).

### 2.13. Роли списком и серверные сессии (миграция 007)
Единственная колонка `users.role` мешала выдать человеку несколько ролей
(например, мастер, который ещё и админ). **Решение:** таблица `user_roles`
(`user_id`, `role`) — связь «пользователь ↔ роль», как `master_services`.
`users` пересобрана уже по знакомой процедуре (см. 2.5) без столбца `role`;
данные перелиты через `INSERT ... SELECT`. Роли читаются **из БД** на каждом
запросе (`rolesOfUser`), проверки — по вхождению (`hasRole`/`requireRole`), а
не по равенству.

Заодно сессии стали **серверными**: токен — случайные 32 байта
(`crypto.randomBytes`), в `sessions.token_hash` лежит его SHA-256, наружу уходит
только сам токен в HttpOnly-cookie. Такой токен можно отозвать (logout удаляет
строку), а утечка дампа БД не даёт готовых токенов. Истёкшие сессии удаляются
фоновым таймером и при старте.

Наконец, настройки продукта (`slot_step_minutes`, `hold_ttl_minutes`) перенесены
из `.env` в `studios` — их правит администратор через API, без перезапуска.

### 2.11. Идемпотентный seed
`seed.js` можно запускать многократно без дублей: данные обновляются по
уникальным ключам (`users.email`, `services.name`, `clients.phone`) либо
вставляются только при отсутствии (график, блокировки, записи). Повторный
запуск печатает `+0 новых`.

### 2.12. Секреты и файл базы не должны попасть в Git
`.gitignore` исключает `.env` и файлы базы (`server/data/*.sqlite*`).
Проверено `git check-ignore`: `server/data/app.sqlite` и `.env` игнорируются
соответствующими правилами и не отслеживаются. `.env.example` не игнорируется
(это шаблон без секретов).

## 3. Драйвер SQLite: `node:sqlite`

### 3.1. Что используем
Встроенный в Node.js модуль **`node:sqlite`** (класс `Database`/`DatabaseSync`).
Внешних зависимостей для работы с БД нет — `server/package.json` не содержит
runtime-зависимостей.

### 3.2. Почему выбрали его
- **Нет нативной сборки.** `better-sqlite3` — нативный модуль; на shared-хостинге
  (BeGet) его установка может потребовать компиляторов. `node:sqlite` поставляется
  вместе с Node.js.
- **Меньше зависимостей и рисков.** `npm ci` не тянет нативные пакеты.
- **Стабильного API достаточно** для наших задач (синхронные `exec`/`prepare`).

### 3.3. Компромиссы, о которых надо помнить
- Модуль официально помечен как экспериментальный: Node печатает
  `ExperimentalWarning: SQLite is an experimental feature`. Это лишь
  предупреждение и не мешает работе (в Node 26 модуль — release candidate).
- API может меняться между мажорными версиями Node — поэтому версия Node
  зафиксирована (раздел 4).
- Нет синтаксического сахара `better-sqlite3` (`db.transaction`, `db.pragma`) —
  см. 2.8.

### 3.4. Настройки подключения (`connection.js`)
- Путь к файлу — из `config.databasePath` (по умолчанию `server/data/app.sqlite`);
  папка создаётся автоматически.
- `PRAGMA foreign_keys = ON` — задано явно (в `node:sqlite` включено по
  умолчанию, но фиксируем, чтобы не зависеть от версии).
- `PRAGMA journal_mode = WAL` — меньше блокировок, лучше параллельное чтение.
- `PRAGMA busy_timeout = 5000` — ждать снятия блокировки до 5 секунд.
- Соединение — singleton на процесс (ленивая инициализация), закрывается в
  CLI-скриптах через `closeDb()`.

## 4. Версия Node.js (важно для деплоя на BeGet)

`node:sqlite` появился в Node.js **v22.5.0**, но до **v22.13.0 / v23.4.0** был
доступен за флагом `--experimental-sqlite`. Чтобы не запускать Node с флагом:

| Требование | Значение |
|---|---|
| В `server/package.json` → `engines.node` | `>=22.13.0` |
| Файл `.nvmrc` в корне | `24` |
| **Рекомендуется на BeGet** | **Node 24 LTS** |

Почему 24: это текущая LTS-ветка, `node:sqlite` в ней без флага, а API уже
устоялся. Node 22.13+ тоже рабочий вариант (минимум поддержки). Всё, что
**ниже 22.13**, использовать нельзя: модуля нет или он под флагом.

Практические заметки:
- Нативный код не используется, поэтому несовпадение минорных версий не
  вызывает проблем со сборкой, но **API `node:sqlite`** зависит от версии —
  версию лучше зафиксировать (через `.nvmrc`/панель BeGet).
- После установки проверьте: `node -v` (ожидаемо `v24.x` или `v22.13+`).
- Предупреждение `ExperimentalWarning` в логах — нормально.

## 5. Памятка ИИ-ассистенту

### 5.1. Как менять схему
1. **Не редактируйте уже применённые миграции.** Изменения — новым файлом
   `server/src/db/migrations/NNN_краткое_имя.sql` с б**о**льшим номером.
2. Пересоберите базу локально: `cd server; npm run db:reset`.
3. Обновите `docs/db-schema.md` (схема) и, при необходимости, этот документ
   (раздел «Журнал изменений»).

### 5.2. Инварианты, которые нельзя нарушать
- Форматы времени/денег — раздел 1.3.
- Статусы записи фиксированы: `pending`, `confirmed`, `cancelled`,
  `completed`, `no_show` (`CHECK`).
- Пароль клиента в таблице `clients` не хранится; для входа — `users` (с ролью
  `client` в `user_roles`), поле только `password_hash` (scrypt, формат
  `scrypt$N$r$p$salt$hash`).
- Роли НЕ хранятся в `users`: у пользователя одна или несколько ролей в
  `user_roles`; проверка прав — по вхождению (`hasRole`/`requireRole`), а не по
  равенству. Приоритет прав при нескольких ролях: `admin` > `master` > `client`.
- В `sessions` НЕ хранится сам токен — только его SHA-256 (`token_hash`) и
  `expires_at`. Токен уходит клиенту в HttpOnly-cookie `sid`.
- Таблицы готовых слотов не существует — свободное время вычисляется.

### 5.3. Переменные окружения (`.env`, образец — `.env.example`)
В `.env` только настройки **окружения**, секретов в коде нет:
`NODE_ENV`, `PORT`, `DATABASE_PATH`, `TZ` (резервный часовой пояс),
`SESSION_TTL_HOURS` (срок жизни сессии, по умолчанию 168), `RATE_LIMIT_MAX`
и `RATE_LIMIT_WINDOW_SECONDS` (лимит частоты входа/регистрации), `TRUST_PROXY`
(доверять `X-Forwarded-For`; по умолчанию выключено), а также
`ALLOW_DESTRUCTIVE` (только для разрешения dev-команд на проде — не выставлять!).
Числовые значения проверяются и при некорректном вводе берётся безопасное
значение по умолчанию (`intEnv` в `config.js`).

Настройки **продукта** живут не в `.env`, а в БД (`studios`) и меняются
администратором через API: `timezone`, `currency`, `opening_time`,
`closing_time`, `slot_step_minutes`, `hold_ttl_minutes`. Прежние переменные
`SESSION_SECRET`, `PASSWORD_HASH_ROUNDS`, `SLOT_STEP_MINUTES`,
`HOLD_TTL_MINUTES` больше не используются.

### 5.4. Проверка после изменений
```bash
npm run db:reset      # в schema_migrations появятся все миграции, БД наполнится
npm run seed          # повторный запуск должен давать "0 новых"
```

## 6. API поверх базы

REST API собрано на встроенном `node:http` (зависимостей нет). Точка входа —
`server/src/api/server.js`, запуск: `npm start` (из папки `server/`). Роутер,
сессии, валидация и бизнес-логика — в `server/src/api/`.

Общие правила:
- Ответы — JSON. Коды: `400` неверные данные, `401` нет входа, `403` нет прав,
  `404` не найдено, `409` конфликт (занятое время, дубликаты), `429` слишком
  много попыток (rate-limit).
- Вход — сессионная cookie `sid`: случайный HttpOnly-токен, в БД (`sessions`)
  лежит только его SHA-256 и срок жизни. Выход удаляет строку сессии. Срок —
  `SESSION_TTL_HOURS` (по умолчанию 168 ч), истёкшие сессии чистятся таймером.
- Роли — списком из `user_roles` (не из cookie). Проверки идут по вхождению
  (`hasRole`/`requireRole`), приоритет прав: `admin` > `master` > `client`.
- Время принимается и хранится в **UTC** (ISO-8601 `...Z`), в часовой пояс
  студии переводится только при отображении (поле `*AtLocal`). Деньги — целые
  копейки.
- Наружу отдаются только нужные поля; `password_hash` и чужие данные не
  возвращаются. Текст ошибок БД, SQL и пути к файлам наружу **не** попадают:
  любые неожиданные ошибки превращаются в обезличенный `500`.
- Вход и регистрация ограничены по частоте (rate-limit) — не более
  `RATE_LIMIT_MAX` попыток за `RATE_LIMIT_WINDOW_SECONDS` секунд с одного IP;
  при превышении `429` и заголовок `Retry-After`. IP берётся из сокета;
  `X-Forwarded-For` учитывается только при `TRUST_PROXY=1` (иначе подделка
  заголовка обходила бы лимит).
- Удержание принадлежит создавшему его пользователю: использовать чужой
  `holdToken` при создании записи нельзя (кроме админа).
- При входе scrypt считается всегда — и для несуществующего email тоже (против
  заголовка-заглушки), чтобы нельзя было определить зарегистрирован ли логин по
  времени ответа.
- Свободное время и удержания: слоты вычисляются «на лету» из графика,
  блокировок, активных записей и действующих удержаний. Удержание живёт
  `studios.hold_ttl_minutes` минут и удаляется по истечении (фоновый таймер +
  очистка на каждом запросе). Шаг сетки слотов — `studios.slot_step_minutes`.
- На каждом защищённом эндпоинте выполняется до трёх проверок: (1) вход,
  (2) нужная роль, (3) право на объект (владелец/участник или админ).

- Запись создаётся по выбранным услугам: на каждую услугу — своя строка

  длительность учитывается при подборе слота.
- Клиент связан с записью через профиль `clients` (совпадение `email`);
  прямой FK между `users` и `clients` в схеме нет.
- Клиент не выбирает `clientId` (берётся его собственный профиль по `email`);
  мастеру `masterId` принудительно подставляется свой; выбирать произвольного
  клиента/мастера может только админ (см. 6.4).
- Профиль клиента заводится один раз и дальше только уточняется:
  - при регистрации профиль по телефону заводится, «ничейный» (созданный
    мастером, `email IS NULL`) забирается новым аккаунтом, а занятый чужим
    аккаунтом телефон даёт `409` — второй аккаунт на чужой телефон не заводится;
  - при создании записи клиент без профиля (аккаунты, созданные до появления
    профилей) присылает `fullName`+`phone`, и профиль заводится по ним; чужой
    профиль по телефону не переписывается — тоже `409`;
  - мастер и админ уточняют имя существующего профиля, но `email` чужого
    профиля не переносят.
- Админ может создать запись **поверх занятого времени**, передав
  `allowOverlap: true`. Признак сохраняется в `bookings.allow_overlap` и
  учитывается триггерами; для остальных ролей это поле игнорируется (см. 6.3).

### 6.2. Защита от двойной записи

Двойное бронирование одного слота закрыто на трёх уровнях:

1. **Триггеры БД** (миграция `005_bookings_no_overlap.sql`, уточнены в
   `006_bookings_allow_overlap.sql`): `BEFORE INSERT` и `BEFORE UPDATE` на
   `bookings` поднимают ошибку `BOOKING_OVERLAP`, если активная (`pending`/
   `confirmed`) запись мастера пересекается по времени с новой или изменяемой.
   Это последний барьер — он срабатывает даже если код обойдёт проверки API.
2. **Транзакция `BEGIN IMMEDIATE`**: при создании и переносе записи блокировка
   на запись берётся сразу (а не при первом изменении), поэтому два параллельных
   запроса не могут одновременно пройти проверку доступности. При любой ошибке
   выполняется `ROLLBACK`.
3. **Обработка в API**: ошибка триггера (`BOOKING_OVERLAP`) и повтор старта
   (`UNIQUE uq_bookings_master_start_active`) превращаются в `409 Conflict` с
   сообщением «Выбранное время уже занято» и `details.nearestSlots` —
   ближайшими свободными слотами (до 5, в пределах 14 дней), чтобы клиент сразу
   переоформился. Текст ошибки БД наружу не показывается.

Проверки доступности и вставка/обновление выполняются внутри одной транзакции,
поэтому между «проверкой» и «записью» не может вклиниться другой запрос.

### 6.3. Осознанное наложение (только админ)

Иногда нужно поставить клиента **поверх занятого времени** (перегруз, личная
просьба). Для этого в `POST /api/bookings` добавлено поле `allowOverlap`.

- **Проверка роли** — в `server/src/api/booking-service.js`, функция
  `resolveAllowOverlap(user, body)`: `if (!hasRole(user, "admin")) return false;`
  (роль читается из `user_roles`). Только роль `admin` может установить
  признак; у клиента и мастера он не читается вовсе.
- Если признак установлен, приложение пропускает собственную проверку
  `isIntervalFree`, а триггер БД пропускает вставку (`WHEN ... AND
  NEW.allow_overlap = 0`). Частичный UNIQUE-индекс тоже исключает такие строки,
  поэтому возможно наложение даже с тем же временем начала.
- Записанный `bookings.allow_overlap = 1` **не** является «невидимой»: при
  проверке пересечений других записей она учитывается как обычная активная
  запись. То есть дальше всё ведёт себя штатно — на неё никто не «наложится».
- Признак не принимается от клиента/мастера: даже если такой запрос придёт, он
  будет проигнорирован, и сработают обычные проверки (→ `409`).

### 6.4. Единая точка создания записи

Запись **всегда** создаётся одной функцией `createBookings(user, body)` в
`server/src/api/booking-service.js` — независимо от роли. Роут
`POST /api/bookings` (`routes/bookings.js`) лишь вызывает её. Различия прав и
доступных полей заданы внутри функции:

| Роль | `masterId` | `clientId` | `allowOverlap` | Кто клиент |
|---|---|---|---|---|
| `client` | обязателен | запрещён (`403`) | игнорируется | свой профиль по `email`; если профиля нет — новый по `fullName`+`phone` |
| `master` | только собственный (иначе `403`) | можно | игнорируется | `clientId` либо новый по `fullName`+`phone` |
| `admin` | обязателен | можно | учитывается | `clientId` либо новый по `fullName`+`phone` |

Сам `INSERT` выполняет единственная низкоуровневая функция `insertBookingRow`
(`server/src/db/bookings.js`); её же использует сид. Другого `INSERT` в
`bookings` в проекте нет — это гарантирует одинаковый набор полей и один путь
через ограничения БД (триггеры, UNIQUE). Перенос (`PATCH /api/bookings/:id`) и
отмена (`POST /api/bookings/:id/cancel`) тоже сведены к функциям
`rescheduleBooking` / `cancelBooking`, а смена статуса админом — к
`setStatusByAdmin` (единая `UPDATE bookings SET status`).

### 6.5. Безопасность

Как устроены девять ключевых требований безопасности:

1. **Пароли (scrypt).** `server/src/auth/password.js`: `node:crypto`
   `scryptSync`, своя соль на каждый пароль, параметры хранятся вместе с хешем
   (`scrypt$N$r$p$saltBase64$hashBase64`), сравнение — `timingSafeEqual`. В
   открытом виде пароль не хранится и не логируется; тестовые пользователи
   сида тоже получают хеш.
2. **Сессии с TTL и хешем токена.** После входа создаётся случайный токен
   (`crypto.randomBytes(32)`), в `sessions` лежит только его SHA-256 и
   `expires_at`. Cookie `sid` — HttpOnly, SameSite=Lax, `Secure` в production,
   `Max-Age` = `SESSION_TTL_HOURS`. Истёкшие сессии удаляет таймер в
   `server.js`; `logout` удаляет строку (токен отзывается).
3. **Роли списком из БД.** Таблица `user_roles`; роли читаются на каждом
   запросе (`rolesOfUser`), проверки — `hasRole`/`requireRole` по вхождению.
   Роль из cookie/тела запроса не берётся.
4. **Три проверки на эндпоинте.** Вход (`requireAuth`), роль
   (`requireRole(ctx, ...roles)`), право на объект (`assertBookingAccess`,
   `assertOwnership` для удержаний): клиент видит только свои записи, мастер —
   свои (из своего расписания), админ — все.
5. **Секреты в `.env`, настройки — в БД.** В коде нет ключей и паролей; в `.env`
   только окружение (`PORT`, `DATABASE_PATH`, `SESSION_TTL_HOURS`,
   `RATE_LIMIT_*`). В репозиторий попадает лишь `.env.example`. Изменяемые
   администратором настройки продукта — в `studios`.
6. **Параметризованные запросы.** Все обращения к БД — через `db.prepare(...)` с
   `?`-плейсхолдерами (`sql.js`, `booking-service.js`, `holds.js` и т. д.).
   Конкатенация пользовательских значений в SQL не используется.
7. **Валидация и отброс лишних полей.** Все входные данные проходят
   `server/src/api/validate.js` (тип, формат, длина, диапазон; даты —
   `dateOnly`/`isoUtc`). Поля, которые роль не вправе задавать (`clientId` у
   клиента, `allowOverlap` у не-админа), не читаются и игнорируются.
8. **Rate-limit входа/регистрации.** `server/src/api/rate-limit.js` — счётчик по
   скользящему окну (IP + корзина). `POST /api/auth/login` и `/register`
   вызывают `rateLimit`; при превышении — `429` и `Retry-After`.
9. **Ошибки без деталей.** `sendError` в `http.js` отдаёт наружу только
   сообщения наших `HttpError`; любой иной сбой (ошибка СУБД, путь к файлу)
   превращается в обезличенный `500`, подробности — только в лог сервера.

Дополнительно по итогам аудита:

- **Регистрация не захватывает чужой профиль.** `clients` вставляется с
  `ON CONFLICT(phone) DO NOTHING`: регистрацией на чужой телефон нельзя
  переписать email существующего клиента и получить доступ к его записям.
- **Создание мастера атомарно.** Услуги проверяются до вставок, а аккаунт,
  роль, профиль и связи пишутся в одной транзакции — «осиротевший» аккаунт
  или профиль при ошибке не остаётся.
- **Разделение ошибок регистрации.** `UNIQUE` трактуется как «email занят»,
  прочие сбои пробрасываются как есть, а не маскируются под конфликт.
