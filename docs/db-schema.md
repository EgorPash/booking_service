# Схема базы данных (SQLite) — сервис онлайн-записи «Lumi Beauty Studio»

Документ описывает проект базы данных для сервиса онлайн-записи.
СУБД — **SQLite**. Это учебный проект, поэтому схема спроектирована минимально
достаточной: под клиентский интерфейс, админ-API и корректный расчёт свободного
времени.

> Соответствует текущему клиентскому интерфейсу (см. `docs/ui-map.md`) и
> админ-разделу (`/admin/*`), который работает с теми же таблицами через
> `/api/admin/*`: услуги, мастера, график и связи «мастер → услуги».

---

## 1. Экраны и какие данные им нужны

| Экран | Что показывает | Откуда берутся данные |
|---|---|---|
| **1. Лендинг** | Студия, услуги и мастера; кнопка «Записаться» | `studios`, `services`, `masters`, `master_services` |
| **2. Авторизация** | Вход, регистрация, текущая сессия | `users`, `user_roles`, `sessions`, `clients` |
| **3. Запись** | Услуги, мастера, даты и свободное время | `services`, `masters`, `master_services`, `master_schedules`, `time_blocks`, `bookings`; свободное время вычисляется |
| **4. Подтверждение** | Данные клиента, удержание слота, создание записи | `clients`, `slot_holds`, `bookings` |
| **5. Запись оформлена** | Номер, услуги, мастер, дата, время, итог | `bookings` в связке с `services`, `masters`, `clients` |
| **6. Личный кабинет** | Активные записи и история клиента | `bookings` в связке с `services`, `masters` |
| **7. Детали записи** | Полная карточка, отмена | `bookings`, `services`, `masters`, `clients` |
| **8. Перенос записи** | Новые дата и время для той же услуги и мастера | `bookings`, `master_schedules`, `time_blocks`, `slot_holds` |

таблицами: `services`, `masters`, `master_services`, `master_schedules`.

Служебные данные, не видимые на экранах напрямую, но необходимые: аккаунты для
входа (`users`), их роли (`user_roles`) и активные сессии (`sessions`).

## 2. Общие соглашения

Единые правила для всей схемы — чтобы данные во всех таблицах хранились
одинаково и их можно было сравнивать, сортировать и фильтровать без сюрпризов.

### 2.1. Формат даты и времени (единый для всей БД)

В SQLite нет отдельного типа «дата/время», поэтому формат выбираем сами.
**Принято правило:**

- **Абсолютные моменты времени** (дата+время, когда происходит запись или
  блокировка) хранятся как **TEXT в формате ISO-8601 в UTC**:
  `YYYY-MM-DDTHH:MM:SSZ`, например `2026-10-22T14:00:00Z`.
- **Даты без времени** — `YYYY-MM-DD` (например `2026-10-22`).
- **Длительности** — целые минуты, `INTEGER` (например, 90).
- **Время внутри повторяющегося недельного графика** — `HH:MM` (24 часа),
  например `10:00`. Это «настенное» местное время, а не момент.
- **Метки создания/изменения строк** (`created_at`, `updated_at`) — тот же
  ISO-8601 UTC.

**Почему именно так:**

1. **Сортируется правильно как текст.** В ISO-8601 порядок строк совпадает с
   хронологическим порядком, поэтому `ORDER BY` и сравнения `>` `<` работают
   без преобразований.
2. **Читается человеком.** Дамп базы сразу понятен, не нужны конвертеры.
3. **Поддерживается SQLite.** Функции `date()`, `datetime()`, `strftime()`
   умеют работать с таким форматом.
4. **UTC убирает двусмысленность.** Нет путаницы с часовыми поясами и
   переходом на летнее/зимнее время.

Местное время студии хранится отдельно в `studios.timezone`
(например, `Europe/Moscow`) и применяется при **показе** и при **сопоставлении
с недельным графиком**, но не в самих «моментах».

### 2.2. Деньги

Все цены — целые числа в **копейках** (минорных единицах), тип `INTEGER`.
Например, 150000 = 1500 ₽. Так исключаются ошибки округления чисел с плавающей
точкой. Валюта — отдельное поле `currency` (ISO-4217, `RUB`).

### 2.3. Идентификаторы и флаги

- Первичные ключи — суррогатные `id INTEGER PRIMARY KEY`.
- Логические флаги (`is_active`) — `INTEGER` со значениями `0`/`1`.
- Названия таблиц — во множественном числе, поля — в `snake_case`.
- Внешние ключи включены (`PRAGMA foreign_keys = ON`) — SQLite их не проверяет
  по умолчанию.

## 3. Список таблиц

| № | Таблица | Назначение |
|---|---|---|
| 1 | `studios` | Настройки студии (одна запись): название, адрес, часовой пояс, валюта, общие часы работы |
| 2 | `users` | Аккаунты для входа; хранится только **хеш** пароля |
| 3 | `masters` | Профили мастеров, которых видно на форме записи |
| 4 | `clients` | Клиенты (имя, телефон) — для повторных визитов |
| 5 | `services` | Услуги: название, описание, длительность, цена |
| 6 | `master_services` | Какие мастера выполняют какие услуги (многие-ко-многим) |
| 7 | `master_schedules` | Повторяющийся недельный график работы мастера |
| 8 | `time_blocks` | Разовые блокировки времени (выходной, обед, личное) |
| 9 | `bookings` | Записи клиентов: кто, к кому, на что, когда, статус |

Помимо предметных таблиц в базе есть служебная `schema_migrations`: её создаёт
прогонщик миграций (`server/src/db/migrate.js`) для учёта применённых миграций
(`name`, `applied_at`). К предметной схеме она не относится и в нумерацию выше
не входит.

Также есть служебные таблицы:

- `slot_holds` (миграция `004_slot_holds.sql`) — временные удержания слота на
  время оформления записи: `id` (токен), `master_id`, `service_ids` (JSON),
  `starts_at`/`ends_at`, `duration_min`, `price_minor`, `currency`,
  `expires_at`, `created_at`, `user_id` (кто удерживает). Это **не** таблица
  заранее подготовленных слотов (см. раздел 6 и «Спорные решения», п. 10):
  удержание живёт несколько минут, учитывается при расчёте свободного времени и
  удаляется по истечении срока.
- `user_roles` (миграция `007_security_hardening.sql`) — роли пользователей
  **списком** (`user_id`, `role`); у одного аккаунта их может быть несколько.
- `sessions` (миграция `007_security_hardening.sql`) — серверные сессии:
  `token_hash` (SHA-256 от токена), `expires_at`; сам токен хранится только в
  cookie клиента.

К девяти предметным таблицам они не относятся.

## 4. Описание таблиц

Обозначения: **PK** — первичный ключ, **FK** — внешний ключ,
«обяз.» — обязательность (`Да` / `Нет` / `Да, по умолчанию ...`).

### 4.1. `studios` — настройки студии

Одна строка с параметрами студии. В проекте студия одна, поэтому таблица
нужна в основном для хранения часового пояса, валюты и общих часов работы,
которые показывает лендинг.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор записи |
| `name` | TEXT | Да | | Название: «Lumi Beauty Studio» |
| `address` | TEXT | Нет | | Адрес (г. Тула) |
| `phone` | TEXT | Нет | | Контактный телефон |
| `timezone` | TEXT | Да, по умолчанию `Europe/Moscow` | | Часовой пояс студии (IANA) |
| `currency` | TEXT | Да, по умолчанию `RUB` | | Валюта (ISO-4217) |
| `opening_time` | TEXT | Нет | | Общее открытие, `HH:MM` (например `10:00`) |
| `closing_time` | TEXT | Нет | | Общее закрытие, `HH:MM` (например `20:00`) |
| `slot_step_minutes` | INTEGER | Да, по умолчанию `30` | | Шаг сетки слотов, минуты (`CHECK (> 0)`) |
| `hold_ttl_minutes` | INTEGER | Да, по умолчанию `10` | | Время жизни удержания слота, минуты (`CHECK (> 0)`) |
| `created_at` | TEXT | Да | | ISO-8601 UTC |
| `updated_at` | TEXT | Да | | ISO-8601 UTC |

> `slot_step_minutes` и `hold_ttl_minutes` — настройки **продукта**: их правит
> администратор через API (`PATCH /api/admin/studio`), а не через `.env`.

### 4.2. `users` — аккаунты

Нужна для входа в систему. **Важно:** хранится только `password_hash`, поля для
самого пароля нет. Ролей в этой таблице **нет** — они вынесены в `user_roles`
(см. 4.2.1), чтобы у человека могло быть несколько ролей.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор |
| `email` | TEXT | Да | UNIQUE | Логин (хранить в нижнем регистре) |
| `password_hash` | TEXT | Да | | Хеш пароля (scrypt). **Сам пароль не хранится** |
| `is_active` | INTEGER | Да, по умолчанию `1` | | Заблокирован ли аккаунт |
| `created_at` | TEXT | Да | | ISO-8601 UTC |
| `updated_at` | TEXT | Да | | ISO-8601 UTC |

### 4.2.1. `user_roles` — роли пользователя (список)

У одного аккаунта может быть несколько ролей (например, мастер, который ещё и
администратор). Роли читаются из БД на каждом запросе; проверки — по вхождению.
Приоритет прав при нескольких ролях: `admin` > `master` > `client`.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `user_id` | INTEGER | Да | PK (составной), FK → `users.id` | Пользователь |
| `role` | TEXT | Да | PK (составной) | `CHECK (role IN ('admin','master','client'))` |

Составной первичный ключ `(user_id, role)` не даёт выдать одну роль дважды.
При удалении пользователя роли удаляются каскадно (`ON DELETE CASCADE`).

### 4.2.2. `sessions` — серверные сессии

Одна строка на активный вход. Наружу (в cookie `sid`) уходит **сам токен**, а в
БД лежит только его **хеш** — утечка дампа не даёт готовых токенов, а logout
удаляет строку (токен отзывается).

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор сессии |
| `user_id` | INTEGER | Да | FK → `users.id` | Чья сессия (`ON DELETE CASCADE`) |
| `token_hash` | TEXT | Да | UNIQUE | SHA-256 (base64url) от токена сессии |
| `created_at` | TEXT | Да | | ISO-8601 UTC |
| `expires_at` | TEXT | Да | | ISO-8601 UTC; истёкшие сессии удаляются |

Индексы: `idx_sessions_user` (`user_id`), `idx_sessions_expires` (`expires_at`).

### 4.3. `masters` — мастера

Профили мастеров (Анна, Мария, Елена), которых выбирает клиент.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор |
| `user_id` | INTEGER | Нет | FK → `users.id`, UNIQUE | Аккаунт для входа (может отсутствовать) |
| `full_name` | TEXT | Да | | Имя мастера («Анна») |
| `title` | TEXT | Нет | | Должность («Топ-стилист») |
| `bio` | TEXT | Нет | | Краткое описание |
| `avatar_url` | TEXT | Нет | | Аватар (в клиентском интерфейсе — инициал) |
| `is_active` | INTEGER | Да, по умолчанию `1` | | Показывать ли мастера в списке |
| `created_at` | TEXT | Да | | ISO-8601 UTC |
| `updated_at` | TEXT | Да | | ISO-8601 UTC |

Связи `master_services` и `master_schedules` удаляются каскадом вместе с
мастером. В админ-разделе удаление «умное»: мастер без записей удаляется
физически, мастер с записями — отключается (`is_active = 0`).

### 4.4. `clients` — клиенты

Данные клиента для записи и личного кабинета. **В этой таблице пароля нет** —
только контактные данные. Учётная запись для входа хранится отдельно, в `users`
с ролью `client`; прямой FK между `users` и `clients` в схеме нет. Клиентский
интерфейс требует входа перед созданием записи.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор |
| `full_name` | TEXT | Да | | Имя клиента |
| `phone` | TEXT | Да | UNIQUE | Телефон в нормализованном виде (`+79991234567`) |
| `email` | TEXT | Нет | | Email (необязательно) |
| `created_at` | TEXT | Да | | ISO-8601 UTC |
| `updated_at` | TEXT | Да | | ISO-8601 UTC |

### 4.5. `services` — услуги

Карточки услуг с лендинга и услуга, выбираемая на форме.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор |
| `name` | TEXT | Да | UNIQUE | Название («Женская стрижка») |
| `description` | TEXT | Нет | | Описание («...с укладкой») |
| `duration_min` | INTEGER | Да | | Длительность в минутах, `CHECK (duration_min > 0)` |
| `price_minor` | INTEGER | Да | | Цена в копейках, `CHECK (price_minor >= 0)` |
| `currency` | TEXT | Да, по умолчанию `RUB` | | Валюта |
| `is_active` | INTEGER | Да, по умолчанию `1` | | Показывать ли услугу |
| `created_at` | TEXT | Да | | ISO-8601 UTC |
| `updated_at` | TEXT | Да | | ISO-8601 UTC |

Записи клиентов ссылаются на услугу внешним ключом, поэтому удалить услугу с
записями нельзя. Админ-раздел различает два случая: услуга без записей
удаляется, услуга с записями — отключается (`is_active = 0`) и исчезает из
каталога и формы записи, но остаётся в истории уже оформленных записей.

### 4.6. `master_services` — мастера ↔ услуги

Связь многие-ко-многим: какие мастера оказывают какие услуги. Именно поэтому
на форме список мастеров зависит от выбранной услуги.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `master_id` | INTEGER | Да | PK (составной), FK → `masters.id` | Мастер |
| `service_id` | INTEGER | Да | PK (составной), FK → `services.id` | Услуга |

Первичный ключ составной: `PRIMARY KEY (master_id, service_id)`.

### 4.7. `master_schedules` — недельный график мастера

Повторяющееся расписание: в какие дни недели и в какие часы мастер работает.
Допустимо несколько интервалов на один день (например, перерыв между утренней и
вечерней сменой).

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор |
| `master_id` | INTEGER | Да | FK → `masters.id` | Мастер |
| `weekday` | INTEGER | Да | | День недели по ISO-8601: 1=Пн … 7=Вс, `CHECK (weekday BETWEEN 1 AND 7)` |
| `start_time` | TEXT | Да | | Начало смены, `HH:MM` |
| `end_time` | TEXT | Да | | Конец смены, `HH:MM`, `CHECK (start_time < end_time)` |
| `valid_from` | TEXT | Нет | | Дата начала действия правила (`YYYY-MM-DD`) |
| `valid_to` | TEXT | Нет | | Дата окончания действия правила (`YYYY-MM-DD`) |
| `created_at` | TEXT | Да | | ISO-8601 UTC |

### 4.8. `time_blocks` — разовые блокировки

Интервалы, когда мастер недоступен: выходной, обед, личные дела, обучение.
Это единственный способ «вычесть» время помимо самих записей.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор |
| `master_id` | INTEGER | Да | FK → `masters.id` | Мастер |
| `starts_at` | TEXT | Да | | Начало блокировки, ISO-8601 UTC |
| `ends_at` | TEXT | Да | | Конец блокировки, ISO-8601 UTC, `CHECK (starts_at < ends_at)` |
| `reason` | TEXT | Нет | | Причина («обед», «отпуск») |
| `created_at` | TEXT | Да | | ISO-8601 UTC |

Выходной день моделируется блокировкой на весь рабочий день.

### 4.9. `bookings` — записи

Главная таблица: конкретная запись клиента к мастеру на услугу.

| Поле | Тип | Обяз. | Ключ | Описание |
|---|---|---|---|---|
| `id` | INTEGER | Да | PK | Идентификатор |
| `client_id` | INTEGER | Да | FK → `clients.id` | Клиент |
| `master_id` | INTEGER | Да | FK → `masters.id` | Мастер |
| `service_id` | INTEGER | Да | FK → `services.id` | Услуга |
| `starts_at` | TEXT | Да | | Начало записи, ISO-8601 UTC |
| `ends_at` | TEXT | Да | | Окончание, ISO-8601 UTC, `CHECK (starts_at < ends_at)` |
| `status` | TEXT | Да, по умолчанию `pending` | | `CHECK` — фиксированный набор (см. раздел 5) |
| `duration_min` | INTEGER | Да | | Длительность услуги на момент записи (снимок), минуты, `CHECK (> 0)`. Миграция `008_booking_service_snapshot.sql` |
| `price_minor` | INTEGER | Да | | Цена на момент записи (снимок), копейки |
| `service_name` | TEXT | Нет | | Название услуги на момент записи (снимок). Миграция `009_booking_service_name_snapshot.sql`; для старых записей восстановлено из `services.name` |
| `currency` | TEXT | Да, по умолчанию `RUB` | | Валюта |
| `comment` | TEXT | Нет | | Комментарий клиента |
| `allow_overlap` | INTEGER | Да, по умолчанию `0` | | `CHECK (0/1)`. Осознанное наложение, поверх занятого времени. Ставит **только** администратор (миграция `006_bookings_allow_overlap.sql`); триггер пропускает такие записи при вставке, но в проверке пересечений других записей они участвуют как обычные. |
| `created_at` | TEXT | Да | | ISO-8601 UTC |
| `updated_at` | TEXT | Да | | ISO-8601 UTC |

**Связи:** клиент, мастер и услуга — обязательные внешние ключи; при удалении
таких справочных записей запись не удаляется (используем мягкое отключение
`is_active`, см. «Спорные решения»).

**Снимок услуги.** В записи хранятся цена, длительность и название услуги на
момент оформления (`price_minor`, `duration_min`, `service_name`), а не ссылки
на текущие значения справочника. Правка прайса, длительности или названия
услуги не меняет уже созданные записи: в карточке записи и в истории остаются
те цена, длительность и название, которые клиент согласовал. Длительность в
существующих записях восстановлена из интервала
`ends_at - starts_at` при переходе на миграцию `008_booking_service_snapshot.sql`,
название — при переходе на миграцию
`009_booking_service_name_snapshot.sql` (из `services.name`).

## 5. Статусы записи — фиксированный набор

Статус — не свободный текст, а **заранее заданный перечень**. Значение поля
ограничено на уровне БД:

| Статус | Значение |
|---|---|
| `pending` | Создана, ожидает подтверждения |
| `confirmed` | Подтверждена |
| `cancelled` | Отменена (клиентом или студией) |
| `completed` | Визит состоялся |
| `no_show` | Клиент не пришёл |

Реализация — через ограничение `CHECK (status IN (...))`. Варианты хранения
обсуждаются в «Спорных решениях».

## 6. Как вычисляется свободное время (без таблицы слотов)

**Отдельной таблицы свободных слотов нет и не должно быть.** Это осознанное
решение: заранее сгенерированные слоты быстро устаревают (появилась запись,
блокировка, изменился график) и их пришлось бы синхронизировать, что ведёт к
ошибкам. Вместо этого свободное время **вычисляется в момент запроса**.

> Исключение — кратковременное **удержание** слота на время оформления
> (таблица `slot_holds`, миграция `004_slot_holds.sql`). Это не заранее
> подготовленный слот, а временная «бронь на пару минут»: она тоже вычитается
> из свободного времени (наряду с блокировками и записями), но истекает и
> удаляется, а не хранится постоянно.

Алгоритм для выбранной услуги, мастера и даты:

1. Взять из `services.duration_min` длительность услуги.
2. Определить день недели для даты **в часовом поясе студии** и выбрать из
   `master_schedules` подходящие интервалы (совпадение по `weekday`, с учётом
   `valid_from`/`valid_to`).
3. Развернуть интервалы в конкретные отрезки времени на нужную дату.
4. Вычесть из них пересечения с `time_blocks` этого мастера.
5. Вычесть пересечения с активными `bookings` (`status` = `pending` или
   `confirmed`) этого мастера.
6. Нарезать оставшиеся промежутки на слоты, кратные длительности услуги
   (шаг сетки, например 30 минут), оставив только те, что полностью помещаются.
7. Вернуть полученный список.

Таким образом свободное время — **производная величина** от трёх источников:
`master_schedules` (график) + `bookings` (записи) + `time_blocks` (блокировки).

## 7. Уникальные ограничения

| Ограничение | Где | Зачем простыми словами | Что сломается без него |
|---|---|---|---|
| UNIQUE `email` | `users` | У одного аккаунта должен быть уникальный логин | Два сотрудника с одинаковым входом — невозможно понять, кто вошёл |
| UNIQUE `user_id` | `masters` | Один аккаунт — один профиль мастера | Дубли профиля привяжутся к одному логину, появится неоднозначность |
| UNIQUE `name` | `services` | В прайсе не должно быть двух «Женская стрижка» | Дубли услуг путают клиента и разбивают статистику |
| PK `(master_id, service_id)` | `master_services` | Нельзя дважды привязать одну услугу к одному мастеру | Дубли в списке мастеров на форме |
| UNIQUE `phone` | `clients` | Один клиент — один нормализованный телефон | Дубли клиентов, «размножение» истории визитов |
| Частичный UNIQUE `(master_id, starts_at)` | `bookings` | Один мастер не может начать две активные записи в один момент | Двойное бронирование одного и того же времени |
| PK `(user_id, role)` | `user_roles` | Одну роль нельзя выдать пользователю дважды | Дубли ролей, неясный результат проверок |
| UNIQUE `token_hash` | `sessions` | Хеш токена однозначно указывает на сессию | Коллизии токенов, доступ не к своей сессии |

Частичный UNIQUE ловит только совпадение старта. Полный запрет **пересечений**
интервалов накладывают триггеры БД (`005_bookings_no_overlap.sql`) — см.
«Спорные решения», п. 15. Условие индекса и триггеров исключает строки с
`allow_overlap = 1` (осознанные наложения администратора).

## 9. Хранение пароля

- В БД есть **только** `users.password_hash`. Поля для открытого пароля нет и
  быть не должно.
- Хеш считается стойким KDF-алгоритмом. Используется **scrypt** из стандартного
  модуля Node.js (`node:crypto`) — без нативных зависимостей (bcrypt/argon2
  пришлось бы собирать на сервере). Соль случайная и хранится внутри строки хеша
  в формате `scrypt$N$r$p$<salt>$<hash>`; отдельное поле соли не нужно.
- Пароль в открытом виде не логируется и не сохраняется нигде.

## 11. Спорные решения

Здесь перечислены места, где был выбор между вариантами, и обоснование.

1. **Статусы: `CHECK`-ограничение против справочной таблицы.**
   Выбрал `CHECK` со списком значений: проще, не требует JOIN, набор всё равно
   защищён на уровне БД. Справочная таблица удобнее, если понадобятся описания,
   порядок и переводы статусов, — тогда её стоит завести отдельно.

2. **Формат времени: TEXT ISO-8601 UTC против INTEGER (Unix) и против REAL (Julian).**
   Выбрал TEXT ISO-8601 UTC: читаемо в дампе, корректно сортируется, работает с
   функциями SQLite. Unix-число компактнее, но непонятно глазами; REAL (Julian)
   даёт дробную точность, не нужную здесь и опасную округлением.

3. **Деньги: INTEGER (копейки) против REAL и TEXT.**
   Выбрал целые копейки: нет ошибок округления. REAL даёт «0.1+0.2»-проблемы,
   TEXT требует разбора при каждом вычислении.

4. **Клиенты: отдельная таблица `clients` против хранения прямо в `bookings`.**
   Выбрал отдельную таблицу: один клиент — много визитов, нужна история и
   повторные записи. Хранить данные в `bookings` — это дублирование.

5. **Уникальность телефона клиента.**
   Выбрал UNIQUE с нормализованным телефоном, чтобы не плодить дубли. Риск:
   один номер на семью — тогда либо снять UNIQUE, либо добавить различение.

6. **`users` для всех ролей против отдельных таблиц `admins`/`masters`.**
   Выбрал одну таблицу `users` — меньше дублирования, проще вход. Роли хранятся
   не столбцом, а связью `user_roles` (см. п. 19): так у аккаунта может быть
   несколько ролей. Раздельные таблицы дали бы более строгие ограничения, но
   больше кода и дублирование аккаунтов.

7. **Связь `masters` ↔ `users`: 1:1 необязательная.**
   Мастер может существовать без аккаунта (страница есть, входа пока нет),
   поэтому `user_id` допускает NULL и уникален, когда задан.

8. **График: повторяющийся недельный против списка конкретных дней.**
   Выбрал недельный (`weekday` + время), т.к. расписание стабильно; а разовые
   отклонения (выходной, обед) закрыты блокировками. Список конкретных дней
   плодил бы записи на каждый день.

9. **Блокировки: единая `time_blocks` против отдельных `day_off`/`extra_hours`.**
   Выбрал единую `time_blocks`: один механизм «вычитания». Выходной — блокировка
   на весь день. Отдельная таблица «доп. часы» не нужна: дополнительное рабочее
   время добавляется строкой в `master_schedules` с `valid_from`/`valid_to`.

10. **Нет таблицы заготовленных слотов.**
    Намеренно отказался: слоты быстро устаревают и требуют синхронизации при
    каждой записи/блокировке/правке графика. Расчёт «на лету» всегда актуален.

11. **`starts_at` + `ends_at` (с `ends_at` явно) против хранения только начала
    и вычисления конца из `duration_min`.**
    Храним `ends_at` явно: он фиксирует фактическую длительность на момент
    записи и не «поедет», если длительность услуги потом поменяют; при этом
    пересечения проверяются прямым сравнением.

12. **`price_minor` в `bookings` (снимок цены) против ссылки на текущую цену.**
    Храним снимок: цена на момент записи не меняется задним числом, если прайс
    обновят. По той же логике в `bookings` появился `duration_min` — снимок
    длительности услуги (миграция `008_booking_service_snapshot.sql`).

13. **Мультистудийность.**
    Сейчас студия одна — хватит таблицы `studios` из одной строки. При росте в
    сеть достаточно добавить `studio_id` во все рабочие таблицы.

14. **Мягкое удаление (`is_active`) против физического удаления.**
    Выбрал флаг: услуги и мастера, на которых есть записи, нельзя удалять, иначе
    порвётся история; отключение флагом сохраняет ссылочную целостность.
    Админ-раздел применяет это правило автоматически: если по услуге или мастеру
    нет ни одной записи — строка удаляется физически вместе со связями
    (`master_services`, `master_schedules`); если записи есть — запись
    отключается флагом, а клиенту объясняется, почему удаление невозможно
    (см. п. 20).

15. **Предотвращение пересечений брони.**
    SQLite не умеет «range exclusion», поэтому частичный UNIQUE-индекс ловит
    только совпадение `starts_at`, но не перекрывающиеся интервалы. Решение
    построено в три уровня. (1) **Триггеры БД** `BEFORE INSERT`/`BEFORE UPDATE`
    (`005_bookings_no_overlap.sql`) поднимают `BOOKING_OVERLAP`, если активная
    запись мастера пересекается с новой/изменяемой, — это последний барьер,
    работающий даже в обход кода приложения. (2) **Транзакция `BEGIN IMMEDIATE`**:
    блокировка записи берётся сразу, поэтому два параллельных запроса не пройдут
    проверку доступности одновременно. (3) **API** ловит ошибку триггера и
    `UNIQUE` и отдаёт `409` с ближайшими свободными слотами. Строгие неравенства
    (`<`/`>`) считают интервалы «вплотную» (15:00–16:00 и 16:00–17:00) не
    пересечением; отменённые записи слот не блокируют.

16. **Алгоритм хеширования пароля: scrypt вместо Argon2id/bcrypt.**
    scrypt встроен в Node.js (`node:crypto`) и не требует нативной сборки
    (bcrypt/argon2 — внешние модули с компиляцией, что усложняет деплой).
    Оба — стойкие KDF; при необходимости смены алгоритма формат строки хеша
    самодостаточен (префикс `scrypt$...`), что позволит ввести версионирование.

17. **Учётная запись клиента (роль `client`).**
    Изначально `users` была только для сотрудников. Добавили роль `client`,
    чтобы клиент мог входить (например, в личный кабинет), не смешивая это с
    таблицей `clients`: контактные данные записи и учётная запись для входа —
    разные сущности. Роль `client` разрешена миграцией
    `003_users_role_client.sql`; ныне хранится в `user_roles` (см. п. 19).

18. **Осознанное наложение поверх занятого времени (только администратор).**
    Иногда нужно «впихнуть» клиента поверх занятости. Введён столбец
    `bookings.allow_overlap` (миграция `006_bookings_allow_overlap.sql`):
    триггеры на `INSERT`/`UPDATE` пропускают такие записи
    (`WHEN ... AND NEW.allow_overlap = 0`), а частичный UNIQUE-индекс исключил
    их из своего условия. Значение выставляет **только** API при роли `admin`;
    присланный клиентом или мастером флаг игнорируется. При этом сама запись
    остаётся активной и в проверке пересечений других записей считается обычной
    занятостью — иначе «наложение» стало бы лазейкой для двойного бронирования.
    Любая вставка строки в `bookings` идёт через единственную функцию
    `insertBookingRow` (`server/src/db/bookings.js`), ей пользуются и API
    (`createBookings` для клиента/мастера/админа), и сид.

19. **Роли списком (`user_roles`) и серверные сессии (`sessions`).**
    Один столбец `users.role` не позволял выдать человеку несколько ролей
    (например, мастер, который ещё и администратор). Поэтому `users` пересобрана
    без `role`, а роли вынесены в таблицу `user_roles` (связь «пользователь ↔
    роль», по образцу `master_services`); на API проверки идут по вхождению
    (`hasRole`/`requireRole`), приоритет прав `admin` > `master` > `client`.
    Сессии переведены со «состояния в подписанной cookie» на серверные: токен —
    случайные байты, в `sessions.token_hash` лежит его SHA-256, поэтому выход
    реально отзывает доступ, а дамп БД не даёт готовых токенов. Изменение внесено
    миграцией `007_security_hardening.sql`; она же перенесла настройки продукта
    (`slot_step_minutes`, `hold_ttl_minutes`) в `studios` и привязала удержания к
    пользователю (`slot_holds.user_id`).

20. **Снимок длительности услуги и «умное» удаление в админ-разделе.**
    (1) В `bookings` добавлен `duration_min` — длительность услуги на момент
    записи (миграция `008_booking_service_snapshot.sql`): правка длительности
    услуги не переписывает уже оформленные записи, как и цена. Существующие
    записи восстановлены из `ends_at - starts_at` (минимум 1 минута), новые
    значения — `NOT NULL DEFAULT 30` с `CHECK (duration_min > 0)`. (2) Удаление
    услуги или мастера в админ-разделе «умное»: без записей — физическое
    удаление (для мастера вместе с профилем; аккаунт удаляется, если роль
    `master` была единственной, иначе роль снимается, а аккаунт остаётся), с
     записями — только отключение `is_active = 0`. Смысл: запись клиента —
     это история, её нельзя разорвать удалением справочника.

21. **Снимок названия услуги и правило «некому выполнять».**
    (1) В `bookings` добавлен `service_name` — название услуги на момент
    записи (миграция `009_booking_service_name_snapshot.sql`): переименование
    услуги не переписывает уже оформленные записи. Значение nullable, старые
    записи восстановлены из `services.name`; при чтении используется
    `COALESCE(b.service_name, s.name)`, поэтому записи, созданные до
    миграции, читаются корректно. (2) Публичный каталог `GET /api/services`
    отдаёт только те активные услуги, которые оказывает хотя бы один
    **активный** мастер (`EXISTS` по `master_services` + `masters.is_active = 1`).
    Смысл: раньше клиент видел услугу без мастера, выбирал её и упирался в
    тупик — записаться было некому. Админский каталог
    (`GET /api/admin/services`) не фильтруется: администрателю нужны все
    услуги, включая отключённые и пока не назначенные мастерам.
