# Журнал подключения клиентского интерфейса

Короткая сводка по собранным страницам: что показывает экран, какие запросы делает и какие поля ответа выводит. Все запросы идут через `web/js/api.js`; ошибки показываются текстом из `message`. В авторизации `details.field` подсвечивает поле, в подтверждении и переносе `details.nearestSlots` даёт ближайшие свободные окна.

Собрано 8 клиентских экранов в `web/` и каркас админ-раздела (`web/admin/`).
Исходный макет `booking-prototype/` использован при вёрстке и удалён; ниже он
указан только как исторический источник. Админ-раздел пока пуст: собраны
шапка, меню разделов и страницы А1–А3, данные к ним не подключены.

## Как запускать

Клиентская часть — статические файлы, сборщика нет. Отдать их и проксировать
`/api/*` на backend можно штатным сервером из папки `web/`:

```
cd server && npm start      # API на :3000
node web/server.js          # клиентская часть на :4100
```

Порт и адрес API переопределяются переменными `WEB_PORT` и `API_ORIGIN`.

## Общая шапка

- **Источник макета (удалён):** шапка из `booking-prototype/index.html` (`#screen-landing`, `#screen-booking`).
- **Файлы:** `web/js/header.js`, `web/css/header.css`; контейнер `<header data-client-header>` есть на всех страницах.
- **Показывает:** логотип, ссылки «Главная», «Записаться», «Кабинет», «Профиль», «Уведомления»; для гостя — «Войти» и «Регистрация», для вошедшего — имя/инициалы и «Выйти» (кнопка выхода в шапке — `id="header-logout-button"`). На узких экранах ссылки убраны в меню-гамбургер. Пользователю с ролью `admin` добавляется ссылка «Админ» (`data-admin-link`) — она ведёт в `/admin/`; у клиента такой ссылки нет.
- **Эндпоинты:** `GET /api/auth/me`, `GET /api/bookings/my`, `POST /api/auth/logout`.
- **Поля ответа:** `client.fullName` из `GET /api/auth/me` — имя и инициалы (профиль клиента); запасные варианты — `bookings[0].client.fullName` и `user.email`. Ответ `logout` (`ok`) не выводится.
- **Примечание:** ссылки «Профиль» и «Уведомления» ведут на `profile.html` и `notifications.html`; этих страниц в `web/` пока нет. Ссылка «Админ» — удобство, а не защита: доступ к разделу проверяет сервер.

## 3. Запись

- **Источник макета (удалён):** `booking-prototype/index.html` → `#screen-booking` («Форма записи»).
- **Файл:** `web/booking.html`, `web/js/booking.js`, `web/js/store.js`, `web/js/booking-time.js`.
- **Показывает:** четыре шага — услуга, мастер, дата, время. Услуги можно выбирать несколько, цена и длительность складываются. На шаге мастера видно, кто не оказывает выбранные услуги. На шаге даты — календарь с отметками свободных дней и дней без окон; на шаге времени — свободные окна по частям дня и поиск ближайшего окна, если на день ничего нет. На узких экранах внизу закреплены итог и кнопка «Далее».
- **Эндпоинты:** `GET /api/services`, `GET /api/masters`, `GET /api/studio`, `GET /api/masters/:id/slots?date=…&serviceIds=…`.
- **Поля ответа:**
  - `services[].id`, `name`, `durationMin`, `priceMinor`, `currency` — выбор услуг и итог.
  - `masters[].id`, `fullName`, `title`, `serviceIds` — карточка мастера и проверка, что он оказывает все выбранные услуги.
  - `slots[].time` — подпись кнопки времени; `slots[].startsAt` и `slots[].endsAt` — выбор окна и строка «визит закончится»; `timezone` — расчёт времени окончания.
  - `studio.timezone` — определение сегодняшней даты; на экране не выводится.
  - `durationMin`, `priceMinor`, `currency` из ответа слотов читаются в состояние, но в интерфейсе не выводятся.

## 4. Подтверждение записи

- **Источник макета (удалён):** — (новый промежуточный экран, в макете его не было).
- **Файл:** `web/confirm.html`, `web/js/confirm.js`.
- **Показывает:** данные клиента (имя, телефон, email — email только для чтения), комментарий, таймер удержания слота, сводку визита с кнопками «Изменить», кнопку «Подтвердить запись». Если у клиента есть профиль, имя и телефон заполняются из него и поля только для чтения; если профиля нет (аккаунт, созданный до появления клиентских профилей), поля пустые и редактируемые, подсказка просит их заполнить — сервер возьмёт из них профиль. При занятом времени показывает сообщение и ближайшие свободные окна; при истёкшем удержании — обновление или выбор другого времени.
- **Эндпоинты:** `GET /api/auth/me`, `GET /api/services`, `GET /api/masters`, `GET /api/studio`, `GET /api/bookings/my`, `POST /api/holds`, `GET /api/holds/:id`, `DELETE /api/holds/:id`, `POST /api/bookings`.
- **Поля ответа:**
  - `user.email` — readonly-поле email.
  - `client.fullName`, `client.phone` из `GET /api/auth/me` — поля имени и телефона; запасной источник — `bookings[].client.fullName` и `client.phone` (берётся первая запись с клиентом).
  - `services[].name`, `durationMin`, `priceMinor`, `currency` — список услуг, длительность и итог; `masters[].fullName` — мастер.
  - `holdId`, `startsAt`, `expiresAt` из `POST /api/holds` — привязка удержания к слоту и таймер; `active`, `expiresAt`, `holdId`, `startsAt` из `GET /api/holds/:id` — проверка и повторное использование.
  - Ответ `POST /api/bookings` не показывается на этой странице, а сохраняется для успеха: `bookings[].id`, `startsAt`, `endsAt`, `durationMin`, `priceMinor`, `currency`.
  - `details.nearestSlots[].date` и `time` — подписи кнопок ближайших окон; `startsAt` и `endsAt` — выбор нового слота.
  - `released` из `DELETE /api/holds/:id` не выводится; `studio.timezone` используется для времени окончания.
  - В `POST /api/bookings` клиент отправляет `fullName` и `phone`, если они заполнены: сервер использует их, когда профиля у аккаунта нет.

- **Файлы:** `web/admin/index.html` (вход в раздел), `web/admin/bookings.html`, `web/admin/services.html`, `web/admin/masters.html`, `web/js/admin.js`, `web/css/admin.css`; страница отказа — `web/admin-denied.html`.

## Что чинили по ходу вёрстки

| Экран | Что было не так | Как исправили |
|---|---|---|
| Общая шапка | На узких экранах пять ссылок не помещались в строку, навигация прокручивалась горизонтально | На `≤720px` добавили гамбургер и выпадающее меню; логотип и действия оставили в строке. Меню закрывается по ссылке, клику вне и Escape; на десктопе навигация прежняя |
| Запись, шаги | Шаги переносились неравномерно: у них была flex-основа 40%, ровной сетки не было | На `≤640px` заменили на сетку 2×2, уменьшили индекс шага и запретили перенос подписи |
| Запись, время | На `≤560px` слоты шли в три колонки, кнопки получались мелкими | Оставили две колонки, задали `min-height: 48px` и крупный шрифт |
| Запись, итог | Итог и «Далее» не были закреплены внизу; первая мобильная панель занимала около 227px, на 320px название услуги ломалось на неудобные строки | Обернули итог, подсказку и кнопки в `.booking-footer`: на десктопе `display: contents`, на `≤720px` — `sticky` снизу. Уплотнили отступы и шрифты (около 160px), на `≤380px` вернули мете отдельную строку |
| Подтверждение | Неавторизованного клиента после входа возвращало в кабинет, а не обратно на `confirm.html` | В `auth.js` добавили `next` (только локальный `*.html`) и возврат на него после входа |
| Детали, отмена | На узком или невысоком экране диалог мог выйти за высоту, кнопки уходили вниз | Ограничили `max-height: calc(100dvh - 24px)`, включили прокрутку `.dialog-inner`, кнопки сделали `sticky` внизу |
| Перенос | На коротком экране кнопки внизу формы были не видны без прокрутки | Панель действий закрепили `fixed` внизу и зарезервировали под неё 88px, чтобы содержимое доскролливалось |

По лендингу, экрану успеха и списку записей кабинета отдельных поломок вёрстки не зафиксировано; список записей изначально сделан карточками, не таблицей.

## Исправления после проверки API и сценариев

Проверка сценариев в браузере и по API нашла две поломки в профиле клиента и
сопутствующие им. Все правки закрыты, поведение зафиксировано регрессионным
скриптом `server/scripts/regression.js` (`cd server && npm test` — скрипт сам
поднимает backend на отдельной базе и ничего не меняет в рабочей).

| Что было не так | Как исправили |
|---|---|
| Клиент, зарегистрировавшийся на занятый мастером телефон, оставался без профиля: `INSERT … ON CONFLICT(phone) DO NOTHING` молча ничего не создавал, и запись оформить было нельзя | В `server/src/api/routes/auth.js` регистрация теперь находит профиль по телефону: «ничейный» (`email IS NULL`) забирает новый аккаунт, занятый чужим аккаунтом — отказ `409` с понятным текстом |
| Клиент без профиля переписывал `full_name` чужого клиента: `ON CONFLICT(phone) DO UPDATE SET full_name = excluded.full_name` | В `server/src/api/booking-service.js` `resolveClientProfile` больше не обновляет чужой профиль — занятый телефон даёт `409`; «ничейный» профиль забирается, а `email` чужого профиля не переносится |
| Подтверждение записи не отправляло `fullName`/`phone`, поэтому клиент без профиля получал ошибку «Поле "fullName" обязательно» | В `web/js/confirm.js` поля имени и телефона заполняются профилем (`GET /api/auth/me`), а без профиля становятся редактируемыми, и их значения уходят в `POST /api/bookings` |
| Имя клиента в шапке бралось только из его записей, кнопка выхода в шапке не имела `id` | В `web/js/header.js` имя берётся из `client.fullName` (`GET /api/auth/me`), кнопке выхода задан `id="header-logout-button"` |
