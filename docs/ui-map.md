# Карта экранов

Клиентский интерфейс собран в `web/` на обычных HTML, CSS и JS, без сборки.
Все запросы идут через `web/js/api.js`; общая шапка подключается из
`web/js/header.js`. Исходный макет `booking-prototype/` использован при вёрстке
клиентских экранов и остался в проекте как исторический источник; ниже —
актуальные экраны проекта.

Собрано **8 экранов клиента** и **4 административных экрана**. Клиентские
экраны описаны в разделе «Экраны», административные — в разделе
«Административные экраны». Backend-эндпоинты `/api/admin/*` уже есть,
клиентских страниц для них пока нет.

## Общая шапка

- **Файлы:** `web/js/header.js`, `web/css/header.css`.
- **Показывает:** логотип, «Главная», «Записаться», «Кабинет»; для гостя —
  «Войти» и «Регистрация», для вошедшего — имя/инициалы и «Выйти». На узких
  экранах ссылки убираются в меню-гамбургер.
- **Данные:** `GET /api/auth/me`, `GET /api/bookings/my`.
- **Действие:** `POST /api/auth/logout`.
- **Заглушки:** ссылки «Профиль» и «Уведомления» ведут на `profile.html` и
  `notifications.html`; этих страниц в текущей итерации нет.

## Основные переходы

1. **Лендинг → Запись.** Выбор услуг, мастера, даты и времени.
2. **Запись → Подтверждение.** Перед созданием записи клиент вводит данные,
   слот удерживается на время оформления. Если клиент не вошёл, его отправляет
   на `auth.html?next=confirm.html`.
3. **Подтверждение → Запись оформлена.** После успешного `POST /api/bookings`
   открывается `success.html` с номером и деталями.
4. **Кабинет → Детали.** Из карточки записи можно открыть детали, перенести
   будущую запись или отменить её.
5. **Детали → Перенос.** Услуга и мастер фиксированы, меняются только дата и
   время.

## Административные экраны

Админ-эндпоинты реализованы в `server/src/api/routes/admin.js`. Каждый требует
роль `admin` (`requireRole(ctx, "admin")`); в отладочном SPA вкладка «Админ»
показывается только пользователю с этой ролью (`test-frontend/app.js`).

Административных экранов в `booking-prototype/` нет — там прямо сказано:
«Ровно три экрана… админка отсутствуют намеренно». Поэтому источник макета для
админ-экранов — отладочный SPA `test-frontend/`: все четыре блока лежат в
секции `#section-admin` файла `test-frontend/index.html`, логика — в
`test-frontend/app.js`. Ниже они перечислены как четыре отдельных экрана: по
правилу «один экран прототипа — одна страница» каждый блок станет своей
страницей в `web/`.

Каркас админ-раздела собран: `web/admin/index.html` — вход в раздел,
`web/admin/bookings.html`, `web/admin/services.html` и `web/admin/masters.html` —
страницы разделов А1–А3. Разделы **А2 «Услуги»** и **А3 «Мастера»** подключены
к данным: списки, формы, отметки «мастер → услуги», график и умное удаление
работают (`web/js/admin-services.js`, `web/js/admin-masters.js`, общие
хелперы — `web/js/admin-ui.js`). Раздел А1 «Записи» пока пустой (только шапка и
заголовок). Экрана А4 (настройки студии) в `web/` пока нет.

### Основные переходы админ-панели

В макете админ-раздел — одна страница с четырьмя блоками, навигации между
блоками нет. При разнесении блоков по отдельным страницам появилась своя
навигация: меню разделов в шапке админ-панели (`web/js/admin.js`) — «Записи»
(`web/admin/bookings.html`), «Услуги» (`web/admin/services.html`) и «Мастера»
(`web/admin/masters.html`); вход в раздел — `web/admin/index.html`. Ссылка на
админку в клиентской шапке (`web/js/header.js`) появляется только у
пользователя с ролью `admin`.

1. **Записи → детали записи.** Администратор открывает любую запись через
   клиентский `GET /api/bookings/:id`, то есть страницу
   `web/booking-details.html?id=<id>`.
2. **Услуги ↔ Мастера.** Список из `GET /api/admin/services` — источник
   селектов услуг на экране мастеров и на форме создания мастера.
3. **Настройки студии → Записи.** Часовой пояс студии определяет, как
   фильтр `date` переводит день в UTC-диапазон, а шаг слотов — сетку окон,
   по которой админ сверяет занятость мастера.

### Доступ к админ-разделу

Права проверяет сервер, интерфейс только показывает результат.

- **Роль приходит списком.** Роли лежат в таблице `user_roles` и читаются из
  БД (`server/src/api/session.js`, `rolesOfUser`). Проверяется вхождение роли
  в список (`hasRole`), а не равенство: у пользователя может быть несколько
  ролей. Выдать роль `admin` через API нельзя — она назначается только в БД.
- **`GET /api/admin/access`** (`server/src/api/routes/admin.js`) — единая
  проверка: администратору `200` и список ролей, остальным `403` с текстом
  «Этот раздел только для администраторов».
- **Страницы `/admin/*` закрывает `web/server.js`**: перед отдачей файла он
  спрашивает у backend `GET /api/admin/access` с cookie сессии. Нет роли —
  ответ `403` и страница `web/admin-denied.html` с тем же сообщением.
  `/admin` без слеша перенаправляется на `/admin/`.
- **Внутри страницы** проверка повторяется на клиенте (`web/js/admin.js`,
  `GET /api/admin/access`): если доступа нет, вместо раздела показывается
  сообщение «Этот раздел только для администраторов».
- **Ссылка «Админ»** в клиентской шапке (`web/js/header.js`) добавляется
  только пользователю с ролью `admin`. Это удобство, а не защита: без роли
  сервер всё равно отдаёт `403`.
- **После входа** клиент попадает в `web/dashboard.html`, администратор — в
  `/admin/` (`web/js/auth.js`).

### Чего не хватает в API

- **А1 «Записи».** Нет списка клиентов: `GET /api/admin/clients` не
  существует, а фильтр принимает только `clientId`, который надо угадать; в
  таблице имя клиента есть, а найти клиента по имени нельзя. Нет постраничной
  выдачи — `GET /api/admin/bookings` возвращает все записи разом (без
  `limit`/`offset`), сортировка только по `starts_at DESC`. Нет фильтра по
  диапазону дат (только один день) и нет поиска по имени клиента или услуги.
  Нет админ-деталей записи (`GET /api/admin/bookings/:id`) — детали смотрятся
  клиентским `GET /api/bookings/:id`. Админ не может изменить время или услугу
  записи: `PATCH /api/admin/bookings/:id` не существует, есть только смена
  статуса. Нет сводки (записей за день, выручка, загрузка) для обзорного
  экрана.
- **А2 «Услуги».** `DELETE /api/admin/services/:id` — умное удаление: без записей
  услуга удаляется физически, с записями — только отключается (`is_active = 0`),
  и ответ объясняет, что произошло; вернуть в работу можно `PATCH` с
  `isActive: true`. Нет `GET /api/admin/services/:id` — карточка берётся из
  общего списка. В ответе услуги есть `bookingsCount` и `mastersCount` (сколько
  мастеров её оказывают), но нет списка имён мастеров — видно только число.
- **А3 «Мастера».** График теперь можно прочитать:
  `GET /api/admin/masters/:id/schedule` отдаёт сохранённый недельный график
  мастера (в форме макета — JSON в текстовом поле). Нет данных об аккаунте
  мастера — в ответе нет ни `userId`, ни email, поэтому нельзя понять, под каким
  email мастер входит. Нет способа создать аккаунт для уже существующего
  мастера: `POST /api/admin/masters` создаёт профиль вместе с аккаунтом, а
  существующий email отклоняется с 409. Нет занятых окон:
  `GET /api/masters/:id/slots` отдаёт только свободные слоты, поэтому день
  мастера нельзя посмотреть целиком.
- **А4 «Настройки студии».** `GET /api/admin/studio` отдаёт `name`, `address`,
  `phone`, но `PATCH /api/admin/studio` эти поля не принимает — название, адрес
  и телефон студии изменить нельзя. В макете эти поля и не выведены.

### Админ-эндпоинты без экрана

Эндпоинтов `/api/admin/*` без экрана нет: все покрыты экранами А1–А4.
Служебный `GET /api/admin/access` данных не показывает — он проверяет права
на вход в раздел.

Отдельно — админ-возможности вне `/api/admin/*`, для которых своего экрана
тоже нет:

- `GET /api/bookings/my` для роли `admin` отдаёт **все** записи студии, а не
  только свои, но показывается на клиентском экране «Личный кабинет».
- `GET /api/bookings/:id`, `PATCH /api/bookings/:id` и
  `POST /api/bookings/:id/cancel` админу доступны для любой записи (просмотр,
  перенос, отмена), но админских экранов у них нет — только клиентские «Детали
  записи» и «Перенос записи».
- Обзорного экрана админ-панели (сводки) нет: ни в макете, ни в API. Вход в
  раздел — `web/admin/index.html`.

## Вне текущей итерации

- **Раздел А1 «Записи»** — страница `web/admin/bookings.html` собрана как
  каркас: есть шапка, меню и заголовок, но списки, фильтры и смена статуса из
  макета ещё не подключены. Экрана А4 (настройки студии) в `web/` нет.
- **Профиль клиента** — отдельного экрана нет; имя и телефон приходят в
  `GET /api/auth/me` (`client.fullName`, `client.phone`), а если профиля у
  аккаунта нет — из `GET /api/bookings/my`, и на экране подтверждения клиент
  заполняет их сам.
- **Уведомления** — отдельного экрана и модели уведомлений нет.
- **Экраны мастера** — в текущую клиентскую карту не входят.

## Ограничения текущего API

- `GET /api/masters/:id/slots` возвращает только свободные окна; занятые окна
  интерфейс не рисует.
- Список доступных дат не отдаётся одним запросом: календарь собирает его
  перебором дат.
- Отдельного `GET /api/services/:id` нет; карточка услуги берётся из общего
  списка.
- `GET /api/services` отдаёт только активные услуги, которые оказывает хотя бы
  один активный мастер: услугу без мастера клиент не видит ни в лендинге, ни в
  форме записи.
