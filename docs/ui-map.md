# Карта клиентских экранов

Документ описывает экраны **клиента** до верстки: что каждый экран показывает,
откуда берёт данные и куда ведёт. Экраны мастера и администратора сюда не входят
(будут позже).

Источники:

- Прототип: `booking-prototype/index.html` (единственный HTML-файл, три секции
  `#screen-landing`, `#screen-booking`, `#screen-confirmation`) и
  `booking-prototype/script.js` (переключение секций, транзиции).
- Карта связей прототипа: `docs/db-schema.md` §1 («Экраны и какие данные им
  нужны») и `docs/database.md` §1.2 («Связь с экранами прототипа»).
- Код API: маршруты в `server/src/api/routes/*.js`, права и сессии —
  `server/src/api/session.js`, ошибки — `server/src/api/http.js`.

Обозначения в карточках экранов:

- **Прототип** — имя файла (секции) прототипа. «—» означает, что в прототипе
  такого экрана нет и его нужно отрисовать с нуля.
- **Данные (GET)** — эндпоинты, которые наполняют экран.
- **Действия (мутации)** — эндпоинты, которые вызывают кнопки/формы экрана.
- **Переходы** — куда ведут ссылки и кнопки дальше.

> Важно про авторизацию: `POST /api/holds`, `POST /api/bookings` и все
> `/api/bookings/*` требуют входа (`server/src/api/routes/bookings.js`,
> `routes/holds.js`). В прототипе входа нет, поэтому в реальном приложении
> сценарий «Записаться» проходит через экран «Авторизация» (если клиент ещё
> не вошёл).

## 1. Лендинг

- **Прототип:** `booking-prototype/index.html` → `#screen-landing` (плюс футер с
  адресом и часами).
- **Показывает:** название студии, адрес, телефон и часы работы; карточки услуг
  (название, описание, длительность, цена); превью «Ближайшая запись»; кнопки
  «Записаться» и «Наши услуги».
- **Данные (GET):**
  - `GET /api/studio` → название, адрес, телефон, `openingTime`/`closingTime`,
    `timezone`, `currency` (публичная версия без админских полей).
  - `GET /api/services` → карточки услуг (`name`, `description`, `durationMin`,
    `priceMinor`, `currency`).
- **Действия (мутации):** нет (только чтение и переходы).
- **Переходы:** «Записаться» → экран «Авторизация» (если не вошёл) либо «Запись»;
  «Наши услуги» — скролл к блоку услуг; логотип/«Главная» → этот же экран.

## 2. Авторизация (вход и регистрация)

- **Прототип:** — (в прототипе не было; отрисовать заново).
- **Показывает:** форму входа (email, пароль) и форму регистрации (имя, телефон,
  email, пароль); сообщения об ошибках; блок «текущий пользователь», если вход уже
  выполнен.
- **Данные (GET):**
  - `GET /api/auth/me` → `user {id, email, roles}`, `masterId`, `clientId` (кто уже
    вошёл; чтобы не показывать форму повторно).
- **Действия (мутации):**
  - `POST /api/auth/login` → `200` + cookie `sid` (или `401` при неверном пароле).
  - `POST /api/auth/register` → `201`, создаёт клиента с ролью `client`.
  - `POST /api/auth/logout` → выход, сброс cookie.
- **Переходы:** успешный вход/регистрация → «Запись» или «Личный кабинет»;
  «Выйти» → «Лендинг»/«Авторизация».

## 3. Запись (и состояние «Подтверждение»)

- **Прототип:** `booking-prototype/index.html` → `#screen-booking` (форма из 4
  шагов) и `#screen-confirmation` (успех).
- **Показывает:** выбор услуги, мастера, даты и времени; при занятом времени —
  ближайшие свободные слоты; итоговую карточку записи со статусом.
- **Данные (GET):**
  - `GET /api/services` → список услуг для шага 1.
  - `GET /api/masters?serviceId=<id>` → мастера, оказывающие выбранную услугу.
  - `GET /api/masters/:id/slots?date=<YYYY-MM-DD>&serviceIds=<id,id>` → свободные
    слоты (`startsAt`, `endsAt`, `time`), а также `durationMin`, `priceMinor`.
  - `GET /api/bookings/:id` → итог и детали после создания (для экрана
    «Подтверждение»).
- **Действия (мутации):**
  - `POST /api/holds` → удержание выбранного слота на время оформления
    (возвращает `holdId`/токен и `expiresAt`).
  - `DELETE /api/holds/:id` → освободить удержание, если клиент ушёл со страницы.
  - `POST /api/bookings` → создать запись (`masterId`, `serviceIds`, `startsAt`,
    `comment`, `holdToken`).
- **Переходы:** «Подтвердить запись» → «Подтверждение»; «Назад» → «Лендинг»;
  «На главную» → «Лендинг»; «Записаться ещё» → сброс и снова «Запись».

## 4. Личный кабинет

- **Прототип:** — (отрисовать заново).
- **Показывает:** список «моих записей» со статусами
  (`pending`/`confirmed`/`cancelled`/`completed`/`no_show`), датой и временем;
  карточку деталей записи; кнопки переноса и отмены.
- **Данные (GET):**
  - `GET /api/bookings/my` → свои записи (`bookingDetail` с
    `startsAtLocal`, `master`, `service`, `status`).
  - `GET /api/bookings/:id` → детали конкретной записи (с проверкой владельца).
- **Действия (мутации):**
  - `PATCH /api/bookings/:id` → перенос на другое время (`startsAt`).
  - `POST /api/bookings/:id/cancel` → отмена записи.
- **Переходы:** карточка записи → «Детали»; «Записаться» → «Запись»; «Профиль» →
  «Профиль»; «Уведомления» → «Уведомления»; «Выйти» → «Авторизация».

## 5. Профиль

- **Прототип:** — (отрисовать заново).
- **Показывает:** данные клиента — email, имя и телефон; при необходимости — роли
  и кнопку выхода / редактирования профиля.
- **Данные (GET):**
  - `GET /api/auth/me` → `user {id, email, roles}`, `clientId`.
  - Имя и телефон клиента **отдельным эндпоинтом не отдаются** (см. список
    «Не хватает данных»).
- **Действия (мутации):**
  - `POST /api/auth/logout` → выход.
  - Редактирование профиля — **эндпоинта нет**.
- **Переходы:** «Назад» → «Личный кабинет»; «Выйти» → «Авторизация».

## 6. Уведомления

- **Прототип:** — (отрисовать заново).
- **Показывает:** напоминания о предстоящей записи, подтверждения, изменения

- **Данные (GET):** нет — в API нет модели и эндпоинтов уведомлений (см. «Не

## 7. Служебные (технические) страницы

- **Прототип:** — (отрисовать заново).
- **Показывает:** состояния ошибок и переходов:
  - `404` — «страница не найдена» (нет совпадения в роутере API);
  - `401` — «требуется вход» (нет cookie/сессия истекла);
  - `403` — «нет доступа» (например, чужая запись);
  - `500` — «ошибка сервера» (обезличенный ответ `sendError`);
  - `409` — «время занято» (со списком ближайших слотов);
  - `429` — «слишком много попыток» (rate-limit входа/регистрации);
  - `502` — «API недоступно» (если фронтенд-прокси не достучался до backend).

- **Действия (мутации):** нет.
- **Переходы:** «На главную» → «Лендинг»; «Войти» → «Авторизация»; «Повторить» —
  повтор последнего запроса.

## Не хватает данных в API

Экраны, для которых текущих эндпоинтов недостаточно:

1. **Профиль** — нет эндпоинта чтения/обновления профиля клиента (имя, телефон,
   email). `GET /api/auth/me` отдаёт только `email`, `roles` и `clientId`.
2. **Уведомления** — нет ни таблицы, ни эндпоинтов уведомлений; экран нечем
   наполнить.
3. **Запись** — нет способа получить список **доступных дат**: `GET
   /api/masters/:id/slots` требует конкретную `date`. Какие дни рабочие, приходится
   определять перебором; «ближайшие слоты» приходят только в теле ошибки `409`
   (`details.nearestSlots`), а не отдельным запросом.
4. **Лендинг/Запись** — нет `GET /api/services/:id` (карточка одной услуги); только
   список `GET /api/services`.
5. **Лендинг** — блок «Ближайшая запись» из прототипа нечем наполнить: нет
   публичного эндпоинта свободных слотов без выбора конкретного мастера и услуги.

## Эндпоинты без экрана

1. **Все `/api/admin/*`** — `GET`/`PATCH /api/admin/studio`,
   `GET /api/admin/bookings`, `PATCH /api/admin/bookings/:id/status`,
   `GET`/`POST`/`PATCH`/`DELETE /api/admin/services`,
   `GET`/`POST`/`PATCH`/`DELETE /api/admin/masters`,
   `PUT /api/admin/masters/:id/services`, `PUT /api/admin/masters/:id/schedule` —
   относятся к экранам мастера и администратора (вне текущей карты).
2. **`GET /api/holds/:id`** — не привязан к отдельному экрану: данные удержания и
   так возвращаются из `POST /api/holds`; отдельное чтение нужно только для
   служебной проверки удержания.

## Решения по расхождениям

Правило: backend не меняем, всё решается на стороне экрана. Для каждого пункта
выбрано одно решение из заданных вариантов.

### Экрану не хватает данных

| Находка | Решение | Почему |
|---|---|---|
| Профиль: нет эндпоинта чтения имени/телефона | **Данные в API на самом деле есть** — `GET /api/bookings/my`: в каждой записи приходит `client { id, fullName, phone }` | Свои имя и телефон клиент уже получает вместе со списком записей, отдельный эндпоинт не нужен |
| Профиль: нет эндпоинта изменения данных | **Убрать элемент из верстки** — профиль только для чтения | Изменить имя/телефон/email на стороне экрана нельзя, а backend не трогаем |
| Уведомления: нет эндпоинтов | **Можно собрать из нескольких запросов** — из `GET /api/bookings/my` построить ленту по статусу и `startsAtLocal`, а адрес и часы для текста взять из `GET /api/studio` | Отдельной модели уведомлений нет, но события «скоро визит», «подтверждено», «отменено» выводятся из своих записей |
| Запись: нет списка доступных дат | **Можно собрать из нескольких запросов** — при открытии шага даты запросить `GET /api/masters/:id/slots?date=…&serviceIds=…` для каждого из ближайших N дней и отметить дни, где `slots` не пуст | Эндпоинт слотов есть, но только на одну дату; календарь набирается перебором дат |
| Лендинг/Запись: нет `GET /api/services/:id` | **Данные в API на самом деле есть** — `GET /api/services`: в списке уже есть `name`, `description`, `durationMin`, `priceMinor`, `currency` | Карточка услуги собирается из общего списка, отдельный запрос не требуется |
| Лендинг: блок «Ближайшая запись» нечем наполнить | **Убрать элемент из верстки** | Публичного эндпоинта слотов без выбора мастера и услуги нет, а показывать придуманные слоты нельзя |

### Эндпоинт без экрана

| Находка | Решение | Почему |
|---|---|---|
| Все `/api/admin/*` (studio, bookings, services, masters, schedule) | **Экран будем верстать позже** | Это экраны мастера и администратора, они вне текущей карты клиента |
| `GET /api/holds/:id` | **Оставить как есть** | Это служебная проверка удержания; отдельный экран не нужен, данные уже приходят из `POST /api/holds` |

---

## Что нельзя решить на стороне экрана

- Редактирование профиля клиента (изменение имени, телефона, email) — нет
  эндпоинта на изменение.
- Реальная отправка уведомлений (email/SMS) и хранение их состояния
  «прочитано» — нет модели и эндпоинтов.
